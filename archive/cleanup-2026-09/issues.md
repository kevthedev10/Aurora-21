# Project 21: open issues

Audit of the C# server under [`localfut/server`](localfut/server), 2026-09-25, at `0a6c1aa` plus the uncommitted work listed under "In progress". Work through these after the in-progress items pass the full suite. **Full suite 2026-09-25 after working through the list:** 383/385 in 34.4 minutes; the two failures are F-2. Record each fix, and the evidence behind it, in [`status.md`](status.md); tick the box here when it is merged.

**Scope and method.** Codebase-wide checks by issue class across roughly 29,000 source lines: async misuse, exception handling, SQL construction, database calls in loops, shared state, input limits and logging. Close reading covered the HTTP request path, the gameplay relay, matchmaking background work, market transactions and the database layer. Gameplay rule code (SBC, Draft, objectives) was sampled, not read line by line. The in-process performance harness does not exercise Kestrel, logging or the `X-UT-SID` header, so issues I-2 and I-3 have never been measured.

Priority: **High** before hosting, **Medium** capacity or robustness, **Low** maintainability.

## High

- [x] **I-1 Relay receive loop stops silently on an unexpected exception.**
  - **Done 2026-09-25:** `HandleDatagram` failures are caught, counted in `RelayAllocation.HandlerFailures` (included in the release log) and logged at the first failure and each tenfold rise; the loop continues. Verified by the relay tests and a log-step test. The recovery path itself is not unit-tested, because no normal input makes the handler throw and a test-only hook was not added.
  - **Where:** `Server/Relay/GameplayRelay.cs`, `ReceiveLoopAsync` (about lines 324–345).
  - **Problem:** The `try` covers only `ReceiveFromAsync`. `HandleDatagram` runs outside it, so any other exception (for example from `.First(...)`) ends that player's loop. The loop was started with `Task.Run` and is not observed.
  - **Impact:** Gameplay traffic in one direction stops mid-match, and nothing is logged.
  - **Fix:** Catch and log around `HandleDatagram` and keep the loop running. Consider counting the failures.
  - **Verify:** A unit test that makes `HandleDatagram` throw once and checks that later datagrams are still forwarded.

- [x] **I-2 An extra database transaction on every `/ut` request for `X-UT-SID`.**
  - **Done 2026-09-25:** `GameContext.UtSid` derives the header once from `Account.Sid`, through the same helper as the UT auth route; `SessionHeaderTests` checks it equals the stored-SID value for two clubs.
  - **Where:** `Server/Http/FutEndpoint.cs`, after routing (`session.Game.ReadAsync(ClubPresentationService.UtSidAsync)`).
  - **Problem:** Every response opens a transaction to read the club SID and hash it (SHA-256). The value is stable for a club session.
  - **Impact:** A pool checkout, BEGIN, a query and COMMIT per request, on top of the route's own work, in a PostgreSQL-bound system. The harness never measures it.
  - **Fix:** The SID is already in memory as `GameContext.Account.Sid`, loaded when the club opens. It is written only at club creation and by `ClearClubAsync`, which only tests call; the offline `reset-club` command recreates the club on the next start. Compute the header from the account once per session, with no database access.
  - **Verify:** A response-header test before and after; a count of transactions per request.

- [x] **I-3 Synchronous, globally locked, flushed log write on every request.**
  - **Done 2026-09-25:** `FileLoggerProvider` queues lines to a shared `BackgroundLineWriter` (one writer task, flush when the queue drains, drain on dispose); the line format is unchanged. Not yet measured through Kestrel.
  - **Where:** `Server/Hosting/FileLoggerProvider.cs` (`lock (_gate)`, `AutoFlush = true`); `FutEndpoint.HandleAsync` logs each request at Information.
  - **Impact:** Request threads serialize on file I/O under load. The harness never measures it.
  - **Fix:** Queue lines to a background writer with batched flushes, and/or lower per-request logs to Debug. Keep errors synchronous if they must survive a crash.
  - **Verify:** A load run through Kestrel, not only the in-process router.

- [x] **I-4 PostgreSQL defaults are sized for one local club.** **Measured 2026-09-25** (1,000 clubs × 2,000 cards, pool 250, paced at 2 requests per player per second, two alternating pairs of the same build; [summary](outputs/performance/hosted-profile-1000-20260925/screen-summary.json)): the hosted profile against PostgreSQL defaults gave PostgreSQL CPU per request **5.059 → 4.914 ms (−2.9%, control spread 1.1%)**, throughput **1,625 → 1,685 requests/s (+3.7%, spread 0.4%)**, harness CPU per request −8.8%, and PostgreSQL private memory 4.3 → 8.4 GB. The p95 of the hub, pack opening, club search and match end was lower in both profile runs than in either control; transfer-market list p95 was mixed. The host stays saturated in both arms (2,000 requests/s requested), so most latency gates still fail. **Recommendation:** use the profile on the hosted server. The pool size stays a separate measurement.
  - **Partly done 2026-09-25:** The harness option `--cluster-config <file>` starts the throwaway benchmark cluster with a deployment profile (it previously ran PostgreSQL's own defaults), and each report records `clusterConfig` and the effective `postgresSettings`. A profile for a 32 GB VPS shared by the server and PostgreSQL is in `tools/Project21.LocalFut.Performance/cluster-profiles/hosted-32gb.json` and the server README (8 GB shared buffers, 20 GB effective cache, 16 MB work memory, 4 GB WAL, 260 connections to match the benchmarks' pool); local-install defaults are unchanged. `ClusterSettings` no longer points at the deleted `SCALABILITY.md`. **Open:** the profile is unmeasured; run the control/candidate comparison (PostgreSQL CPU per request, one sitting, PC otherwise idle) before adopting it. Choosing the hosted `max_pool_size` is a separate measurement.
  - **Where:** `runtime-source/localfut21/config.example.json` (`cluster_shared_buffers_mb` 32, `cluster_max_connections` 30, `max_pool_size` 10, `cluster_effective_cache_size_mb` 512, `cluster_work_mem_mb` 4).
  - **Problem:** The hosted server and PostgreSQL share one VPS. A hosted database of several GB needs a larger cache, more connections and a bigger pool. The benchmark's throwaway cluster used PostgreSQL defaults, not these settings.
  - **Fix:** Add a documented hosted profile (for example sized to the VPS memory) without changing the local-install defaults. Then run the 1,000-club profile against a cluster that uses it.
  - **Verify:** A controlled A/B of PostgreSQL CPU per request and throughput.

## Medium

- [x] **I-5 Market list reads use two or three transactions.** **Done 2026-09-25:** `ReadExpiringAsync` checks the view's trades and reads the view in one transaction; only when a listing is due does it expire those rows (same timestamp as before) and read again. `MarketViewsUseOneTransactionWhenNothingIsDue` counts transactions for status, watchlist and transfer list; the market, budget, parity and maintenance tests passed 53/53.

- [x] **I-7 Relay allocates per packet.**

- [x] **I-12 Unknown FIFA requests are answered with a successful empty response and logged on every occurrence.**
  - **Done 2026-09-25:** `UnknownRequestLog` (shared on `GameContext`, present when `debug_unknown_http` is on) writes `logs/unknown-requests.jsonl` (16 MB cap, one rotation) and `logs/unknown-requests-summary.json` (every 30 s when changed, and at shutdown); the main log names each new endpoint once. `UnknownRequestLogTests` covers grouping, counting, redaction, rotation and the router behaviour.
  - **Where:** `Core/Web/FutRouter.cs` (end of the route loop, about lines 155–162); `debug_unknown_http` (default `true` in `config.example.json`).
  - **Behaviour:** An unmatched request returns `200` with `{}` and `X-LocalFUT15-Unknown: 1`, so the client treats it as success. With the default setting, every occurrence is logged at Warning with method, path and a body preview. They are not silently discarded.

    - Keep a per-path summary, `logs/unknown-requests-summary.json`, with first seen, last seen, count and one example. Rewrite it periodically and at shutdown, for review after each live test.
    - In the main log, write one line per **newly seen** method and path, pointing to the dedicated file, instead of a Warning per call.
    - Safeguards: a size cap with rotation, so a hosted server cannot fill the disk. Leave out query values and credential-like body fields (tokens, auth, sid, password), per the `AGENTS.md` rule against collecting real credentials or sensitive traffic. The files live under the git-ignored logs directory; confirm with `Test-RepositoryHygiene.ps1`.
    - Continue to honour `debug_unknown_http`, which now switches the dedicated file on or off.
  - **Verify:** Router tests showing repeated unknown calls append JSONL lines, update the summary counts, and log only one main-log line per new path; a redaction test for credential-like fields; a rotation test at the size cap.

## Second audit: game rules and economy (2026-09-25)

Close reading of the store, pack opening, player picks, Draft, SBC, objectives, match settlement, daily drop, quick sell and item moves (about 4,000 lines). **Every entry below comes from reading the code; none is reproduced by a test yet.** Fix each one by first writing a test that fails.

Many of these are local-server conveniences: on a single-player install the player owns the whole economy anyway. On a hosted server with a shared transfer market, free coins and packs reach other players through the market, so the E items are **High before hosting**.

### Economy (hosted: High)

- [x] **E-1 A pack purchase can skip payment with `useCredits`.** **Fixed 2026-09-25:** an unowned pack is always paid for, in points when requested and otherwise in coins; owned packs still open free from My Packs (the native `useCredits=0`, `PREORDER` request). Reproduced first by `StoreEconomyTests`. `StoreService.BuyAndOpenPackAsync` (about lines 199–205): `useCredits` is read from the request (`IsTruthy(request.GetOr("useCredits", 1))`). A request for a pack the club does not own, with currency COINS and `"useCredits": 0`, sets both `usePoints` and `useCredits` to false: nothing is charged, and the pack is generated. **Fix:** an unowned pack is always paid for, in points when points are requested and in coins otherwise; drop the flag or reject a request that declines both.
- [x] **E-2 Unknown pack ids open a free default pack.** **Fixed 2026-09-25:** `GetPackConfig` returns an empty object for an unknown id, so the existing checks refuse it (400). Reproduced first (the request returned 200). `PackSettings.GetPackConfig` always adds `_special_weights` (line 52), so the result is never empty, and the `config.Count == 0` checks in `StoreService.OpenPackBodyAsync` and `PackOpeningService.CreatePackAsync` can never fire. An unknown id falls through to a player pack with default settings (12 cards, gold) and price 0. **Fix:** check that the pack exists (a store pack or a reward pack) before adding derived keys; reject everything else.
- [x] **E-3 Reward packs, and disabled store packs, can be bought by id.** **Fixed 2026-09-25:** only packs `PackSettings.IsForSale` accepts (enabled store packs) can be bought; reward packs open only when owned. Reproduced first for both. Reward-pack configs have no `price`, so buying one by id costs 0 (objective, SBC and player-pick reward packs). `BuyAndOpenPackAsync` also never checks `enabled`, so a disabled store pack is still for sale. **Fix:** only enabled store packs can be bought; reward packs open only from My Packs (`ownedReward`).
- [ ] **E-4 Match-end rewards can be claimed without playing.** **Deferred 2026-09-25 to the Python-version port**, which the maintainer says changes match end. No captured FIFA match-end body exists locally (the only logged request has no body), so which id the client echoes back is unverified; verify it before tying settlement to server-created matches. `MatchService.EndMatchAsync` protects against replays with a settlement key, but the key is the client's `matchId`, `gid` or `matchReportId`. Nothing checks that this club created that match, so each made-up id pays the match coins and objective progress again. When the body has no id and no match was created in the current session, there is no replay protection at all. **Fix:** record created matches server-side (id, club, created time) and settle only an open match of this club, once.
- [x] **E-5 Draft entry is free with any currency other than coins.** **Fixed 2026-09-25:** FIFA Points pay the rules' points price; other currencies (Draft tokens: the club has no token inventory) are refused with 400. The insufficient-points reason text is not from a client capture. `DraftService.PurchaseEntryAsync` charges only when the request's currency is COINS or CREDITS; any other value, such as POINTS, starts a run for free (commented "other currencies are free locally"). **Fix:** charge points or Draft tokens by the entry rules, or refuse unsupported currencies.
- [x] **E-6 A Draft rearrangement can copy one picked card into several slots.** **Fixed 2026-09-25:** a rearrangement must use every current pick exactly once (`DRAFT_REARRANGEMENT_CHANGES_PICKS`), and a player pick lands in the slot its choices were generated for. The captain keeps the slot the confirmation names: captain choices fit any position, and the offline scenario places the captain at position 10. `DraftService.RearrangeAsync` checks only that each placed card is one of the run's picks (`RelationalDraftStore.PickedItem`), not that each pick is used once. A squad of eleven copies of the best pick is accepted, and a partial list silently drops picks. **Fix:** a rearrangement must be a permutation of the current picks. `ChooseAsync` similarly accepts any `positionId` for a pick instead of the slot the choices were generated for; restrict it to `currentPositionId`.

### Database cost (PostgreSQL CPU, the capacity lever)

- [x] **P-1 Item moves cost about four statements per item.** **Fixed 2026-09-25, measured:** "Store all" was 13 statements for one card and **123 for twelve**; each duplicate check also scanned every owned player in the club. The batch now reads the items, their live listings and the owned cards of just their players once, applies the moves in order in memory, and saves once: **11 statements for any size** (`StoringAPackHasAConstantQueryBudget`). `ItemMoveTests` pins the ordering (a second card of the same player in one batch becomes a duplicate) and passed on the old code first. The Unassigned list (`GET /purchased/items`) and the single-card duplicate check (player-pick confirmation) now index only the players they look up instead of the whole club. `ApplyItemUpdatesAsync` reads the item, checks for a live listing, checks for a duplicate and saves, per item; `UpdatePileAsync` then reads the item again. "Store all" after every pack sends 12 or more items: about 50 statements on a path every pack opening takes. Batch the reads (items, listed ids and owned duplicates for the whole batch) and save once.
- [ ] **P-2 SBC squad loads cost two statements per player.** `LoadSbcPlayersAsync` runs `GetItemAsync` and `LiveMarketListingForItemAsync` per id (about 22 for 11 players), on save and again on submit; `ConsumeSbcPlayersAsync` deletes one by one. Low traffic, so lower priority.
- [ ] **P-3 Draft requests write the last-used slot every time.** `SlotForAsync` runs a write transaction on every Draft request that names a slot, even when it is unchanged. Write only when it changes.
- [ ] **P-4 Smaller repeats.** "Claim all" objectives re-reads and re-saves the objective state per objective. A player-pick reveal reserves one item id per choice instead of one batch.
